# W6 - Browser M45 algorithm logic vs original research replay

## Question and what the result means

W6 asks a narrow, reproducible question:

> Given the EXACT SAME ordered 33-point pose landmark arrays and
> media frame timestamps, does the incremental M45 algorithm used in
> the W2 browser demo emit the same event timestamps as the unchanged
> original M45 research comparator?

This is **algorithmic same-input parity**. It is NOT proof that
the deployed browser MediaPipe Tasks Vision pose estimator outputs
the same landmarks as the frozen Python MediaPipe Solutions
model on the same video. It is NOT a real Chrome/Safari GPU
performance comparison, camera FPS test, user exercise accuracy
estimate, publication TEST evaluation or movement safety measure.

The original W2 synthetic tests already compare small hand-crafted
landmark sequences. W6 extends those regression tests, and M53
additionally arranges a **real TRAIN-only**, owner-run audit on the
20 frozen original M46 replication videos. The original
M45/M39/M34 code remains frozen and unchanged.

## Two distinct parity comparisons

For the original M47 offline Python pose trace:

1. **Direct same-input:** original M45
   detectRelativeExcursionEvents(frames)
   versus W2 LiveRelativeExcursionCounter.consumeSample
   on every identical landmark array and timestamp.
   Count exact event-timestamp differences.
2. **W2 sampling gate:** feed the original trace into
   LiveRelativeExcursionCounter.observe, which retains
   only samples at least 200ms after the previous sampled
   frame. Compare the incremental event timestamps to
   the original M45 comparator evaluated on **that same
   W2-gated subset**. Also record how many samples the
   gate drops; if the gate drops input frames, the original
   full-trace detector might count differently from a
   gated detector, and that is a sampling effect, NOT an
   algorithm mismatch.

At nominal 400ms, the input is **every other frame from
the SAME 200ms Python pose tracking pass**, matching M46.
It is not a separately decoded or tracked 400ms source.

No method adjusts M45 thresholds based on discrepancy.
The original 155-degree high, 35-degree excursion,
400-12000ms recovery and 1250ms tracking gap are
unchanged. A nonzero disagreement must be reported
without being suppressed or called an accuracy score.

## Owner-run one-pass integration with M53

Execute the command in
[docs/M53_TRAIN_NORMALIZED_COUNT_METRICS.md](M53_TRAIN_NORMALIZED_COUNT_METRICS.md).
It verifies the original M49 gate and M46 reference, then
replays the original M47 video comparator on precisely
TRAIN hash ranks 21-40.

The W6 Node process reads private temporary JSON pose
traces already generated by the frozen Python evaluator.
It outputs only two-cadence **aggregate counts**:
source frames, selected/dropped samples, detected
event counts, event-time disagreements and number of
videos containing such disagreements. No raw pose
frames, GT indices, event timestamps, filenames,
participant metadata or original videos are copied
into the public website.

Owner-local summary file:
data/processed/w6_train_same_landmark_parity.json

This file is Git-ignored, not a public research
website source until the owner executes and verifies
it. W5 currently says real browser/Python parity
is **unverified**; do not replace that caveat with
a synthetic-test result.

## Regression and acceptance

~~~bash
cd ~/Desktop/Gym-Pose-Detection-System
git pull --ff-only
npm test --prefix web
python -m pytest tests/test_m53_w6_train_metrics_parity.py -q
~~~

W6 synthetic JS tests check:
- Exact reference rule constants and event times.
- Completed, partial and overlapping cycles.
- Missing pose frames, side changes and tracking gaps.
- Dense input and 200ms gate dropped-frame accounting.
- Only 2-cadence aggregate output, no video/GT/pose storage.
- Rejection of malformed or nonchronological pose input.

W6 does not alter W1-W5 UI, does not use new camera
permissions, does not record a user's webcam, and
does not enable remote RF inference.

## What is still needed for browser/Python end-to-end parity?

A future W6b protocol could, with authorized original
TRAIN-only clips, run the real browser Tasks Vision
model on those clips and compare estimated landmarks
with original offline Python Solutions landmarks under
a predeclared frame alignment and timestamp policy.
That is a separate model-pipeline study. It must
be approved separately and must not use TEST to
choose model versions, sample cadence or thresholds.

Even true same-input algorithmic parity does not
prove model- or runtime-parity, clinical safety,
athlete-independent generalization or publisher
TEST performance.
